# 经验

本文总结当前架构的有效做法、被否定的做法、已知上限和移植要点。架构本身见 [架构](架构.md)，单个缺陷怎样修补见 [缺陷修补](缺陷修补.md)。

## 生成链的事实

恢复以这些事实为依据。它们来自 Unity 2022.3 的真实构建（Android Release 三个 ABI、Windows x64 Release）和随编辑器分发的 libil2cpp 头文件。

- **C++ 只有一份。** 一次构建只执行一次 IL → C++，ARMv7、ARM64、x86_64 共用同一份 C++ 和 `global-metadata.dat`。
  - 字段偏移由编译器按 `offsetof` 计算，C++ 中没有写死指针宽度。
  - Windows 与 Android 两边共有的函数中，99.4% 的 C++ 逐字相同。不同的部分是全程序索引（虚表槽号、RGCTX 下标）和少数 BCL 平台方法。
- **il2cpp 逐方法做模板展开，基本不优化。** 判空、越界、类初始化、元数据惰性初始化、虚表与接口分派、装箱都写成固定序列，所以可以先归一为运行时操作（L2）。
- **`_inline` 副本决定了大部分内联。** il2cpp 为访问器、运算符、`List<T>.Add` 等小方法在每个用到它的翻译单元生成一份 `_inline` 副本。
  - 这些副本标为 `IL2CPP_MANAGED_FORCE_INLINE`：在 clang 上是 `always_inline`，一定被内联；在 MSVC 上只是 `inline`。
  - 调用方中出现的不可访问成员访问，主要来自这些副本。被调方法带注册入口的定义也在产物中，可以作为证明的模板。
- **编译参数。**
  - Android：`-Os -mllvm -hoist-common-insts=1`。后一项让 SimplifyCFG 把两臂开头相同的指令提到分支之前，被内联方法的前缀因此会出现在无关分支之前。
  - Windows：MSVC 的 `/Ox`。
- **平台差异在后端。** 用自写用例的 307 个方法比较 ARM64 与 x86_64：
  - 98% 以上的函数调用序列与条件分支数相同；
  - 差异来自指令选择（例如同一个 `select`，一边是 `cneg`，一边是 `lea`）、落地块的排布、少数内联决定和 switch 的降级。

## 有效的做法

1. **为生成器的每种变换建一个模型，而不是为每种机器码形态加一条规则。**
   - SROA 与寄存器打包 → 位来源代数；
   - 栈着色与溢出 → 帧单元的内存 SSA；
   - SimplifyCFG 的合并与下沉 → φ 的符号值与需求驱动的路径拆分；
   - InstCombine → 规范化；
   - 内联 → 以被调方法为证据的等价证明。

   形态是变换组合的结果，数量随组合增长；变换的种类是有限的。
2. **在构造时规范化。**
   - 移位、掩码、扩展、截断、寄存器对和向量车道，都在符号值构造时改写成切片与拼接；
   - 0/1 值、比较方向、下标扩展等也在构造时归一。

   下游各层看不到这些写法，比较保持严格，不放宽。
3. **一个概念只有一处事实来源。**
   - 帧内存、效果、值投影、运行时操作的语义各定义一次，其余层只查询；
   - 下降是机械的，不保存跨语句状态，也不识别形态。
4. **用规则表和不动点代替手工排列的次序。** 规则依赖另一条规则的结果时，在下一轮自然看到；达到上限的情况作为诊断可见。
5. **内联逆先写语义，再实现。**
   - 写入不是事件，只在观察点上比较堆；
   - 两侧的项属于不同命名空间；
   - 复核（展开新调用后与原方法体共同执行）是唯一的采纳标准。

   这样就不需要为每种出口形态、写入次序各加一条容忍规则。
6. **证明不足就报洞。**
   - 缺口写明第一处不成立的原因，是待补模型的清单；
   - 不把失败改写成另一种标记，也不写执行不到的占位语句。
7. **度量去遮挡。**
   - 只统计独立洞，按原生字节加权，再统计“只差这一类”的方法数，以此决定先补哪个模型。
   - 共享规则的改动要看全量：除了状态变化，还要看 CIL 变化清单和逐文件的 `goto`、语句数。过度拆分不改变状态，只在形态指标上可见。
8. **验证与写出分开。**
   - 执行对照：原生码在模拟器中执行，CIL 由解释器执行，比较事件与堆；
   - 模型检查写成性质（“有字节没写就不能装箱”），而不是写成某个样本的结果。

## 被否定的做法

| 做法 | 问题 |
|---|---|
| 以通用反编译器的伪代码为底层 | 伪代码不提供位来源、帧复用、内联证明所需的证据，IL2CPP 的形态要在伪代码上重做一遍 |
| 先把指令集语义做全 | 投入停在与目标无关的完备性上，没有触及托管语义 |
| 直接写 C# | 不能接受 ILVerify 与执行对照的检验；先写 CIL 再反编译 |
| 每种形态一个文件或分部类 | 规则数随组合增长，并行修改时语义冲突 |
| 共享的可变上下文、名为分析却改写 IR 的步骤 | 插错位置时别的方法退化，回退难以归因 |
| 在下降后的方法体上锁步比较内联 | 每种写法差异都要一种出口分类或交换尝试，放宽后又要收紧 |
| 零差异门禁、棘轮账本 | 迫使新结构复刻旧缺陷；账本自身成为负担。改用影子运行，分歧查清后切换并删除旧实现 |
| 为救单个方法改写共享规则 | 回退大多出在这里，修正几乎都是收窄条件，说明缺的是精确的模型 |

## 已知上限

- **信息下界。** 局部变量名、源码级控制结构、被裁剪的成员、被常量折叠的分支，在产物中已经没有了。上限是语义等价、结构接近源码。
- **等价不可判定。** 守卫、拆分、内联都是程序等价问题，只能在规范形和搜索范围内证明。内联尚不支持带循环或异常区域的模板、调用序列和多入口区域。
- **帧对象的生存期。** 同一帧槽先后承载不同类型的值、`stackalloc` 区域、finally 闭包按引用捕获帧槽，需要把帧对象按生存期建模。
- **结构化依赖反编译器。** `goto` 与未提升的状态机，只能通过让 IL 符合 C# 编译器的规范形来间接改善。
- **验证覆盖。**
  - 执行对照只覆盖抽样与改动影响到的方法，是单线程的；
  - 完全共享泛型的方法不能对照；
  - 写出数不等于语义正确。
- **样本。** 模型的类别来自生成器，是通用的；但预算、阈值和各类缺口的比例是在单一样本上调出来的。

## 移植

- **代码构成。** 约 91% 的代码与指令集无关。ARM64 相关的部分有：
  - `Machine/Arm64` 的解码与提升；
  - 事实层按 32 位指令字做的指纹（约 1k 行，不经过 IR）；
  - AAPCS64 的参数分类；
  - `TPIDR_EL0 + 40` 的栈保护与线程静态的识别；
  - 少数把 `Gpr(0..2)` 当作第 i 个实参的硬编码。
- **先做 Android x86_64。** 编译器、ELF、Itanium 异常模型和 Bionic 都不变，只换指令集和 SysV ABI。栈保护在 `fs:0x28`，同为 Bionic 的槽 5。事实层的指纹应改为先提升、再在 IR 上匹配。
- **Windows x64 的变化更大。** 编译器（MSVC 的优化形态、`/OPT:ICF` 折叠）、ABI（Win64）和异常模型（funclet）三项同时变化，`_inline` 副本也不再强制内联。依据 clang 形态写的 L2 与恢复规则需要逐项重新核对。
- **跨 Unity 版本。** 运行时结构的偏移应由对应版本的 libil2cpp 头文件给出，不写死某一版的常量。
