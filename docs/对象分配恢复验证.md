# 对象分配恢复验证

## 恢复规则

- 从已识别的分配辅助函数和 `TypeInfo` 确定具体引用类型，保留泛型实参。未知、开放、抽象、接口、值类型、字符串、数组和委托不套用普通对象分配。
- `ObjectAllocationValue` 表示清零分配与类型初始化，不表示实例构造完成。后续字段读写、对象传出和构造调用保持原位置。
- CIL 后端使用目标元数据已有的 `Type.GetTypeFromHandle`、`FormatterServices.GetUninitializedObject`；有静态构造函数时保留显式 `RunClassConstructor`，不依赖 `BeforeFieldInit` 的执行时机。
- 分配与紧邻的同类型实例构造调用可以合并为 `newobj`，前提是没有静态构造函数，参数是已经求值的局部、普通参数或常量。不能跨过调用、存储或读取，不能提前读取新对象的字段，也不能合并另一个接收者的构造。
- 被内联的构造函数、跨块构造、有静态构造函数及其他尚无合并证明的路径仍保留独立步骤。不能为了生成 `new T()` 而凭空补一个默认构造函数。
- 全量清单记录分配地址、具体类型和已合并的构造函数；`calls` 仍包含合并后的实际构造目标。

当前 ARM64 输入中，生成代码的 `0x49c8830` 经 `0x49f7770` 跳转到分配主体 `0x49f7a88`；主体在分配之后调用类初始化 `0x49c4710`。导出 `il2cpp_object_new`（`0x49c1d74`）另有捕获异常并返回空值的路径，因此不能仅凭内部目标相同而当作直接抛出异常的分配。识别时排除带异常区域的此类包装。输入哈希同[静态字段恢复验证](静态字段恢复验证.md)，元数据哈希已重新核对。

## 执行检查

合成检查执行生成的 CIL，覆盖：

- 数值字段为零、引用字段为空、重复分配产生独立对象，且不调用实例构造函数。
- `BeforeFieldInit` 类型的一次性初始化，以及初始化失败的传播和缓存。
- 构造前先写字段、传出对象并观察字段，再执行实例构造；构造失败仍保留此前逃逸的对象和副作用。
- 相邻构造合并及整数边界参数；中间调用、对象字段参数、不同接收者和静态初始化的拒绝合并；构造尾调用的返回。
- 普通分配辅助函数与捕获异常的导出包装区分；缺失或错误 `TypeInfo` 拒绝恢复。

无构造分配和相邻构造合并同时执行 ILSpy 输出的 C# 重编译结果。复杂分离式构造只验证 CIL，未宣称其 C# 已支持。

真实 `Sekai.Mysekai.MysekaiLocalCacheData..ctor`（`0x55d31ac`）恢复整个方法体：基类构造、分配并构造 `Dictionary<MysekaiToolType, int>`、保存字段。CIL 和 C# 重编译均创建两个独立空字典，并验证其中一个写入后另一个不变。宿主只映射实际字段与枚举类型，字典使用当前 CLR；没有手写替代恢复方法体，没有加载 Unity。

既有构造回归也通过：`Sekai.Api.GetSuiteUserPartsApi..ctor` 的完整 64 位字段，以及 `0x5631084 → 0x56310e4` 构造委托的 CIL/C# 参数、位型、求值和异常顺序。

## 证据与边界

全量输出为 `artifacts/recovered-allocation-complete/`，精确比较为 `artifacts/allocation-comparison.json`。构建、执行与构造回归日志分别为 `allocation-final-build.log`、`allocation-final-check.log`、`allocation-constructor-regression.log`；源码检查为 `compile-allocation-complete.log`、`compile-allocation-graphics.log`、`compile-allocation-color.log`。生成物不提交 Git。

分离式分配是保留原操作顺序的中间表示，仍需继续恢复完整构造片段。当前 CLR 检查没有证明 Unity 中的实际行为，也没有验证资源耗尽、GC/终结器、所有跨线程类初始化和不同运行时内部的分配时机。类型初始化异常与对象逃逸的已验证范围以上述执行样本为准。
