# 元数据与数组恢复验证

## 恢复规则

- 区分元数据槽位地址和槽位内容。直接读取按编码令牌解析；GOT 间接读取必须有加载器重定位记录，目标也必须是有效元数据槽位。
- 只传播 64 位读取和来源一致的 SSA 汇合。不同类型、未知来源和窄读取保持未恢复。元数据地址不能作为普通 CLR 对象返回。
- 字符串槽位恢复为 `ldstr`，保留 UTF-16 内容和字符串驻留行为。
- 数组分配使用已识别的 `NewArray` 辅助函数及调用处的数组类型信息。长度仍来自原调用参数；即使分配结果无人使用，也保留分配和异常行为。
- 当前数组规则用于 `SZARRAY`。模型与输出另行保留 rank=1 的 `ARRAY`，不能仅凭维数相同将两者合并。
- 64 位 IL2CPP 数组的长度位于 `+24`，元素起始于 `+32`。只有完整元素宽度、匹配的元素步长和可恢复的下标才生成元素操作；不把长度位置当作可写字段。
- 数组读取仍保留在原定义处。输出使用 CLR 数组指令处理判空、越界及引用数组的写入类型检查。

共享泛型调用使用调用处的 MethodInfo 选择具体方法，同时核对方法定义、参数、返回值和隐藏参数的传递位置。元数据与目标不符时拒绝恢复。引用类型共享代码的唯一登记项也可能只是 `object` 占位实例，缺少 MethodInfo 时不能直接采用它。

这些处理位于托管恢复层，不改写机器 SSA。仍未覆盖对象分配与构造合并、装箱、静态字段、数组内部指针的循环归纳、部分元素访问、普通多维数组操作，以及位于栈上的隐藏 MethodInfo。

## 执行检查

合成检查覆盖：

- 元数据直接读取、GOT 间接读取、相同和不同来源的汇合，以及地址冒充对象、类型冒充方法、分配缺少参数等反例。
- 数组分配、尾调用、默认元素、重复分配的独立身份；未使用结果时仍抛出负长度异常。
- 整数、对象、浮点数组读写；读取后再写入的顺序；空值、越界、协变写入检查及 NaN、负零位型。
- 字符串中的中文、空字符、换行、引号、反斜杠、代理项和驻留身份。
- CLR 回读后仍区分 `T[]` 与 `T[*]`。

真实方法使用匹配的二进制与元数据恢复，输入哈希同[值布局验证](值布局验证.md)：

| 方法 | 地址 | 验证 |
| --- | --- | --- |
| `PathUtility.GetFileCombinePath` | `0x55d2b5c` | 调用下方真实恢复方法，检查空输入、多段路径、反斜杠、中文和空引用 |
| `PathUtility.GetSlashCombinePath` | `0x55d2ac4` | 组合路径后，以元数据中的 `\\` 和 `/` 执行替换 |
| `ScreenLayerMysekaiCanvas.get_ContentListTypes` | `0x5acb814` | 分配长度为 1 的枚举数组，写入 `13` 并返回；多次返回的数组互不影响 |
| `CutScenePresenter.CleanupCamera` | `0x57a3694` | 静态核对同一共享目标的两次调用分别使用 `CutSceneFovAdjustor` 和 `Animator` |

前三个方法执行真实恢复出的 CIL，没有手写替代方法体。路径方法的 `Path.Combine` 和 `string.Replace` 使用当前 CLR，不能据此证明 Android 与 Windows 路径库的所有平台差异。数组方法的宿主只提供对应枚举定义。没有加载 Unity。

`CleanupCamera` 的检查只验证调用解析和泛型实参，没有执行 Unity 组件删除。

## 全量结果

| 项目 | 数量 |
| --- | ---: |
| `Sekai.Mysekai`、`Sekai.Api` 全部代码 case | 23,390 |
| 可形成托管方法体 | 9,329 |
| 写出 CIL 的目标 case | 8,778 |
| 相比 `5a95e8b` 新增 / 回退 | 623 / 0 |
| 尚未写出 CIL | 14,612 |
| 回读通过的方法定义，含访问器依赖 | 8,915 |

前后地址集合与方法定义对应完全一致。新增完整方法体均来自 `Sekai.Mysekai`；`Sekai.Api` 已全量检查，但本轮没有新增完整方法体。

1,747 个目标源码文件中有 268 个变化：主程序集 267 个，URP 程序集 1 个。主程序集的 1,701 个目标文件和 URP 的 3 个目标文件均为零编译诊断错误；两程序集各有 2 项、4 项既有范围外错误。其余三个程序集的 43 个目标文件逐字节未变。

`runtime-check` 与 `body-check` 执行通过。数组类型区别修正后再次运行全部 case，输出源码与修正前逐字节一致，并重新检查了主程序集和 URP 编译诊断。其他新增方法未逐一执行，依赖仍可能是骨架，以上数量不表示完整业务链已经可运行。

最终证据位于 `artifacts/recovered-runtime-vector/`；日志为 `runtime-vector-build.log`、`runtime-vector-check.log`、`runtime-vector-body-check.log`、`runtime-vector-bodies.log`、`compile-runtime-vector.log` 和 `compile-runtime-vector-urp.log`。生成物不提交 Git。
